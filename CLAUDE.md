# Projectory — notes pour Claude

- Mono-repo : `server/` (Fastify 5, ESM, `node:sqlite`, aucune dépendance native) et `web/` (React 19, Vite, Ant Design 6). Une seule image Docker : le serveur sert `web/dist`.
- UI bilingue FR / EN : le texte français est la source et sert de clé. Front : `t('Texte {var}', { var })` (`web/src/i18n/`, dictionnaire `en.js`) ; serveur : `tr()` (`server/src/i18n.js`, dictionnaire `i18n-en.js`) pour les erreurs, le changelog, ntfy et les entrées de la boîte de réception. Libellés dans des constantes : traduire au rendu, jamais au chargement du module. Toute nouvelle chaîne doit être ajoutée au dictionnaire anglais : `node web/scripts/i18n-keys.mjs --check` et le test serveur `i18n.test.js` le vérifient.
- Commentaires de code en anglais.
- Schéma : ajouter une migration en fin de tableau `MIGRATIONS` dans `server/src/db.js`, ne jamais modifier une migration existante.
- Colonnes JSON (tags, links, version_sources, forum_sources, github, versions, labels, assignees, mine, pr_state, checklist, item_templates) : stockées en texte, décodées par `decode()` ; `pickUpdate()` les sérialise.
- node:sqlite refuse `undefined` et les booléens : passer `null` / `0|1`.
- Statuts « ouverts » des éléments : `OPEN_STATUSES` (`db.js` pour le SQL, `labels.js` côté front) — ne jamais réécrire la liste à la main. Liens entre éléments : table `item_links` (`blocked_by`, `duplicate_of`, `relates_to`) ; quand un élément est terminé, `unblockDependents` (`server/src/items.js`) repasse à « À faire » ceux qu'il bloquait. Une PR liée (`items.pr_url`) fusionnée fait passer l'élément « En test » (synchro) ; la fermeture de l'issue ne touche pas un élément en test, c'est la publication de la version qui le clôt.
- Hors ligne : le service worker (`web/public/sw.js`) sert les GET de l'API depuis le cache quand le réseau manque ; `api.post` met en file (`localStorage`, `flushOutbox`) seulement les créations `/items` et `/docs`.
- Synchro (`server/src/sync/`) : toute nouveauté passe par `pushInbox` avec une `external_key` unique ; la première synchro d'une source est « baselinée » (marquée lue) via la table `settings`.
- `pushInbox` remplit aussi `fresh` (entrées nouvelles et non lues) : c'est ce qui part sur ntfy en fin de `syncProject` (`sync/notify.js`). La CI ne génère une entrée qu'aux changements d'état (vert → rouge, rouge → vert).
- Forges (`server/src/sync/forges/`) : un adaptateur par forge (github, gitlab, gitea — Forgejo = gitea) avec la même interface (`fetchRepo`, `fetchCi`, `latestRelease`, `createIssue`, `listOwnerRepos`). Toujours passer par `forgeFor(db, project)` qui résout le token (comptes `config:forges` puis variables d'env). `whoami()` (compte du token) et `fetchMentions` (GitHub) remplissent `github_items.mine` (author, assignee, review, mention) pour les filtres « Me concernant » et la page « Mon GitHub » (`/api/my-github`) ; `fetchPrState` (GitHub) remplit `github_items.pr_state` pour ces PR, et les transitions sur les PR de l'utilisateur deviennent des entrées `pr_status`. Un bug venu du forum fermé par la synchro crée une entrée `forum_reply` (`items.forum_replied_at` une fois répondu). Sujets suivis : table `forum_watches` (`fetchTopic`, entrées `forum_followed`). CI GitHub : seuls les runs `push` / `merge_group` comptent, GitLab ignore les pipelines `schedule`. Portée par projet : `projects.github_scope` (auto | all | mine) → `projects.mine_only` (recalculé par `refreshMineOnly` et à la synchro) ; toute requête qui compte ou liste les `github_items` passe par `VISIBLE_ITEM` (`server/src/visibility.js`). Checklist de release : `milestones.checklist`, modèle dans `config:release_checklist`. Noms historiques : la table `github_items` et la colonne `projects.github` contiennent les données de toutes les forges.
- Source de version `repo` = releases du dépôt du projet (toute forge) ; `github` = autre dépôt GitHub.
- Tâches planifiées (`server/src/jobs.js`, tick 60 s) : résumé hebdo ntfy (`insights.js`) et sauvegardes `VACUUM INTO` (`backup.js`, `BACKUP_DIR`). Le flux `/api/calendar.ics?token=` échappe à `APP_PASSWORD` (clé dans `config:calendar`). Statistiques : `fetchActivity` des forges, agrégées par `stats.js`.
- Pièces jointes (`server/src/uploads.js`) : fichiers dans `UPLOADS_DIR` (défaut `DATA_PATH/uploads`), référencés uniquement depuis le Markdown (`/api/uploads/<fichier>`), sans table ; les orphelins sont supprimés au moment de la sauvegarde. Côté front, `MarkdownInput` remplace `Input.TextArea` pour tout champ Markdown. Vue « Aujourd'hui » : colonne `items.focus_date` (`server/src/today.js`).
- Réglages applicatifs : `getConfig` / `setConfig` (clés `config:*` de la table `settings`). Le token ntfy n'est jamais renvoyé au front (`token_set`).
- Les tests suppriment `GITHUB_TOKEN` & co de l'environnement : garder ce bloc en tête de chaque fichier de test.
- Après une mutation côté front, appeler `notifyChange()` pour rafraîchir les composants qui écoutent (`useApi(url, { listen: true })`).
- Tests : `cd server && npm test` (fetch simulé, base en mémoire) et `node --test .github/scripts/*.test.mjs`. Build front : `cd web && npm run build`. Workflows : `actionlint`.
- Commits : préfixes `feat:` / `fix:` — le workflow Release s'en sert pour classer le changelog. Ne pas modifier la version des `package.json` à la main : c'est le workflow Release qui le fait.
